# Coordinator input guide

This guide explains the meaning of every fixed input surface for the data-selection
Coordinator. The package is immutable and scoped to one Run and one Coordinator
Call. Read `input/manifest.json` first: it is the authority for which files are
present, their digest, and their source reference. A path not declared there is
unavailable, even if it exists in the workspace.

## Identity and action

- `input/manifest.json`: package identity, `data_selection` task, Coordinator
  scope, basis revision, and declarations for every other file. It is a
  verification ledger, not research evidence.
- `input/action.json`: the current action and the Harness-assigned
  `target_plan_id`. Copy that Plan ID into the proposal; do not allocate or
  replace it.
- `input/task.json`: task-level objective, fixed candidate-pool and dataset
  constraints, portfolio limits, allowed references, and availability facts.
- `input/task/resolved.json`: the resolved task configuration generated by
  Runtime. It contains the task-specific fixed controls and reference values;
  it is configuration, not a source of additional Run facts.

## Run facts and research evidence

- `input/memory/manifest.json`: identity, parent, sources, and declared files
  for the complete Run Memory version frozen for this Call.
- `input/memory/MEMORY.md`: the complete cross-Plan synthesis and primary
  navigation entry. Preserve its stated provenance and uncertainty.
- `input/memory/outcomes/` and `input/memory/findings/`: attributed updates and
  accepted Plan Memories already merged into this RM version. Inspect the
  relevant sidecars before relying on a completed Plan, comparator, or
  contradiction; unrelated historical sidecars need not be reread.
- `input/subject/PLAN_CATALOG.md`: Run-global planning history. It contains
  accepted directions, active intents, and source-eligible completed results.
  Accepted/active directions help avoid repetition; only completed
  source-eligible results may support a historical relation.
- `input/subject/ranking.json`: Harness-owned ranking projection, including
  metric, direction, revision, score, accepted revision, artifact reference,
  and source eligibility. It is a fact to use, not a value to edit.
- `input/subject/portfolio-target.json`: the profile-matched global best frozen
  at Planning Call start. Use it to distinguish hypothesis success from
  portfolio progress; Harness binds it directly and never replaces it with a
  completion-time best.
- `input/subject/budget.json`: total and remaining Plan/Trial capacity and the
  current configured bounds. State the resulting exploration/exploitation
  posture, but never allocate or reinterpret budget.

## Declared task views and resources

The manifest may declare task-specific views such as candidate records,
trajectory statistics, token counts, duplicate groups, contamination or
truncation signals, replay evidence, prior Plan/artifact views, and published
baseline evidence. These are the only available detailed data sources. Read
their local manifest/metadata and preserve their IDs and provenance; do not
scan outside the declared paths or synthesize unavailable fields.

`input/resources/` contains additional fixed, explicitly authorized reference
files. Resources are read-only context, not a place to discover undeclared
data or modify the Run.

## Retry-only inputs

- `input/retry.json`: structured violations and the exact semantic paths that
  may change.
- `input/prior-delivery/`: the previous Attempt's delivery. Preserve unaffected
  files byte-for-byte and change only the named paths.

The Coordinator may read only `input/` and writes only `output/plan.md` and
`output/decision.json`. It must not read repository code, `runs/`, Engine logs,
operator-only data, another Plan's private workspace, or modify RunState.
